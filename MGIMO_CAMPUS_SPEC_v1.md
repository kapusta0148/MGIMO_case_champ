## 1. Цель, аудитории, ценность

Создать работающий в браузере личный кабинет студента, оптимизированный для ширины **360 px** и более; жюри проходит сквозной путь: вход → «Сегодня» → уведомление о переносе → актуальное расписание → заявление/справка → статус после перезагрузки → другой студент не видит чужих данных. Параллельно создаём кабинет сотрудников для изменения демонстрационных учебных данных и заявок. Отличительная идея — персональный учебный календарь с AI Planner и наглядная динамика успеваемости.

**Критерии конкурса:** идея, использование ИИ в создании, имплементация, качество (до 10 баллов каждый). Приоритет: реальная работоспособность и безопасность > полнота обязательного ядра > удобство > инновации > декоративные возможности.

**Дедлайн:** 22.11.2026 23:59 МСК (цель команды — 21.11). Проверить актуальный регламент: https://challenge.mgimo.ai/rules . Сервис должен работать как минимум до 28.11.2026 и открываться из России без VPN.

- Старт: проекта ещё нет, имеется исходный `CLAUDE.md`.

- Дизайн: молодёжный **премиум**, на согласование представить **три авторские визуальные системы**; Claude Code автономен после согласования дизайна.
- Хостинг: **российский VPS/платформа, предел 500 ₽ в месяц**, провайдер окончательно не определён. Сначала сравнить актуальные итоговые цены и ресурсы, не покупать без согласия. GitHub Pages не запускает Flask; для общей ссылки предпочтительнее один HTTPS-домен с React и API.

- Сотрудник деканата: панель заявок, поиск/фильтры, история обработки и статистика; возможность публикации объявлений и редактирования расписания в пределах полномочий.
- Данные: автоматическая генерация вымышленных профилей для новых демонстрационных студентов, заранее подготовленные **минимум 2** различающихся студента + сотрудники.
- Заявки: несколько типов, статусы, комментарии, история, безопасная загрузка и скачивание PDF/JPEG/PNG (дополнительная генерация справки PDF не обязательна).
- Уведомления: расписание, оценки, статусы заявок, дедлайны; внутри приложения и Web Push при технической возможности. Если browser push недоступен — полноценная внутренняя система остаётся рабочей.
- Дополнительные функции: аналитика успеваемости и умный учебный календарь (планировщик).
- Claude Code: максимальная автономность в реализации и тестировании, но **согласование выбора дизайна, расходов и архитектурных решений, влияющих на безопасность/развёртывание**.

## 3. Предлагаемая архитектура (подтвердить перед созданием проекта)

```text
Браузер (мобильный/ПК)
    └── HTTPS, один origin
          ├── / → React/Vite build + Tailwind + Motion (статические файлы)
          └── /api/* → Flask + Gunicorn (JSON API)
                            ├── PostgreSQL + SQLAlchemy + Alembic
                            ├── закрытое хранилище вложений на сервере
                            ├── планировщик: алгоритм, ограничения, рекомендации
                            ├── серверный прокси к AI provider (опционально)
                            └── Web Push sender (опционально)
```

**Ориентиры реализации:** Vite, React Router, TanStack Query для кеша запросов; Flask application factory, SQLAlchemy, Alembic, Marshmallow/Pydantic или равноценная серверная валидация; Postgres; pytest; Playwright; Docker Compose; Caddy/Nginx с TLS; Gunicorn, а не Flask dev server в production. Использовать поддерживаемые версии и фиксировать зависимости.

**Небольшой VPS:** модель и frontend build не должны постоянно занимать память сервера. Отдельно измерить RAM с Postgres + Gunicorn + proxy и выставить ограничения; сборку React по необходимости делать в CI/локально. Не закладывать дорогие очереди/Redis без доказанной необходимости.

**Хостинг-гейт:** сравнить минимум 2–3 варианта по 30-дневной итоговой цене с IPv4, диском, TLS/доменом, резервными копиями (если отдельно), RAM, CPU, стабильностью, возможность доступа из России. Строго <=500 ₽/месяц либо сначала запросить изменение бюджета. Окончательная покупка/деплой с финансовыми последствиями — только после согласия Димы.

## 5. Экраны и пользовательские сценарии

### Публичные / общие
- `/login` — вход по демо-логину и паролю, демонстрационные подсказки для жюри без реальных секретов в открытом коде.
- `/register` — регистрация **демонстрационного** студента без настоящих ФИО, телефона и email. Сгенерировать фантазийные ФИО/группу/оценки/расписание/дедлайны серверно из набора фиктивных данных; запретить выбор сотруднической роли. Ограничить число регистраций/IP и файловую квоту.
- `/profile` — ФИО, факультет, направление, курс, группа и явная отметка «Демонстрационный профиль».
- 404, 403, offline/error, skeleton loading; отсутствие горизонтальной прокрутки на 360 px.

### Студент
1. **`/today` — главный экран:** следующая пара, изменения, задачи дня, ближайший дедлайн, статус последней заявки, уведомления; переходы в реальные разделы за 1–2 действия.
2. **`/schedule` — расписание:** сегодня/неделя, преподаватель, аудитория, время; явно показаны старое и новое значения при переносе, единый источник данных с уведомлениями.
3. **`/grades` — успеваемость:** предметы, оценки, зачёты, сессия, простые графики динамики с объяснимыми расчётами; никаких синтетических «точных прогнозов» без основания.
4. **`/requests` + `/requests/new` + `/requests/:id`:** несколько типов обращений; подача, история статусов, комментарии и вложения, персональный доступ.
5. **`/notifications`:** входящие новости, переносы, дедлайны, результаты; переходы к объекту, «прочитано» сохраняется.
6. **`/calendar`:** недельный/месячный обзор академических событий, личные задачи, отметка выполнения, перенос, предложения алгоритма/ИИ, явное подтверждение на запись.
7. **`/planner`:** анализ известных дедлайнов и добровольно введённых задач, рекомендации по приоритетам и свободным окнам, объяснение «почему», ручное применение. При недоступном AI API — локальный алгоритм остаётся доступен.
8. **`/settings`:** статус разрешения на push, подключение/отключение уведомлений, выход.

### Сотрудники
- **`/staff`** — сводка и счётчики заявок, фильтры, сроки обработки (считаются по фактическим данным).
- **`/staff/requests` и `/staff/requests/:id`** — открыть в разрешённой области, читать безопасные вложения, комментировать, перевести статус по разрешённому переходу, журнал изменений.
- **`/staff/announcements`** — создание/редактирование объявлений с ограничением адресатов.
- **`/staff/schedule`** — переносы/изменения занятий; публикация в расписании и связанном уведомлении из одной транзакции.
- **`/teacher/courses` и `/teacher/courses/:id/grades`** — список только назначенных дисциплин/групп; изменение оценок с проверкой и audit log.
- **`/admin/demo-users`** — безопасное создание/деактивация демонстрационных аккаунтов, без просмотра чужих паролей.

## 7. Контракт API — базовые маршруты

Ответы JSON, ошибки с безопасными сообщениями и машиночитаемыми кодами; дата/время ISO-8601. Пути ниже — ориентир, не требование к точному именованию, но функционально должны быть покрыты.

**Auth:** `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, CSRF token endpoint/механизм.

**Student:** `GET /api/me/dashboard`, `GET /api/me/schedule?from=&to=`, `GET /api/me/grades`, `GET /api/me/requests`, `POST /api/me/requests`, `GET /api/me/requests/:id`, `POST /api/me/requests/:id/attachments`, `GET /api/me/attachments/:id/download`, `GET /api/me/notifications`, `PATCH /api/me/notifications/:id/read`, `GET /api/me/calendar`, CRUD `/api/me/tasks`, `POST /api/me/planner/suggest`, `POST /api/me/planner/suggestions/:id/apply`, `POST/DELETE /api/me/push-subscriptions`.

**Dean:** `GET /api/staff/requests`, `GET /api/staff/requests/:id`, `POST /api/staff/requests/:id/transition`, CRUD `/api/staff/announcements`, `PATCH /api/staff/lessons/:id`.

**Teacher:** `GET /api/teacher/courses`, `GET/PATCH /api/teacher/courses/:id/grades` — каждый курс и студент должны находиться в разрешённом назначении.

**Admin:** минимальный набор управления демо-аккаунтами, под контролем роли и аудита.

Перед реализацией API разработать авторизационную матрицу и единый формат ошибок.

## 8. AI Planner: функциональные правила

1. **Deterministic-first:** сервер собирает данные только текущего студента: его расписание, сроки, оценки и личные задачи; считает свободные интервалы, пересечения дедлайнов и нагрузку простым объяснимым алгоритмом. Не делает медицинских или психологических выводов.
2. **LLM layer (опциональный, настоящий):** через серверный API предлагает текстовые рекомендации и пример плана на основе **минимального** обезличенного учебного контекста. API-ключ только в серверных секретах; не передавать лишние персональные поля.
3. **Безопасность промптов:** заметки студента, комментарии и вложения — недоверенный ввод; игнорировать содержащиеся в них инструкции к модели, не давать модели доступ к секретам и административным функциям.
4. **Права:** модель не может напрямую писать оценки, расписание или статусы заявок. Любые изменения личных задач после предложения требуют явного подтверждения студента и обычной серверной проверки полномочий.
5. **Устойчивость и бюджет:** тайм-аут, ограничение запросов на пользователя/IP, кэширование безопасных ответов, предельный бюджет **300 ₽/мес.** и аварийный рубильник; при исчерпании бюджета — режим алгоритмов, без ошибки основных функций.
6. **Честность:** отличать «правило», «рекомендацию модели» и реальную оценку/событие; не утверждать, что прогноз является гарантией экзаменационного исхода.

## 9. Уведомления и Web Push

- In-app уведомления создаются из серверных событий (перенос, новая оценка, переход заявки, дедлайн) и всегда доступны в кабинете.
- По возможности Web Push через Service Worker и VAPID (ключи в окружении; публичный ключ VAPID может быть на клиенте, приватный — нет); согласие пользователя спрашивать по явному действию; вести реестр подписок по пользователю.
- **Ограничения:** HTTPS, поддержка браузера, на некоторых мобильных устройствах — установка PWA на домашний экран/отдельные условия; никакой гарантии доставки. Отображать причину недоступности и не ломать главный сценарий.
- Рассылку напоминаний о дедлайнах планировать отдельным простым периодическим заданием, без дублирования событий.

## 10. Безопасность и данные

- Не использовать реальные персональные и академические сведения, реальные институтские интеграции, лого. Не просить вводить настоящие ФИО/email/телефон; регистрация явно «демо».
- Пароли — Argon2id или стойкий проверенный хешер с солью; никакого plaintext в базе, логах, git, frontend. Для жюри учётные данные выдавать отдельно в комментарии к работе, не в публичном репозитории. `.env.example` только с заглушками.
- Сессии — серверная идентификация текущего пользователя, secure/httponly/samesite cookie на HTTPS, CSRF-защита запросов изменения состояния, ограничение частоты логина, выход с инвалидированием сессии, безопасная обработка 401/403.
- Обязательное серверное разграничение: другой студент не прочтёт профиль, оценки, файлы или заявки, даже изменив ID. Преподаватель не изменит оценку чужого курса. Сотрудник деканата видит только назначенные обращения и данные.
- Файлы: предел размера/количества, проверка типа по содержимому, allowlist PDF/JPG/PNG, UUID-имена, вне директории публичных файлов; download только после авторизации и проверки конкретной заявки; заголовки загрузки с `attachment`, защита от path traversal, очистка небезопасного имени, квоты и удаление. Не включать реальные документы.
- Валидация всех форм на бэкенде, безопасный вывод текста, подготовленные запросы ORM, ограничение объёма полей, ограничения регистрации и общего хранилища, запрет debug mode в production, безопасные заголовки и HTTPS.
- Резервное копирование Postgres и вложений; миграции и проверяемое восстановление для размещённой версии.
- Логировать ошибки с request ID и техническим контекстом без паролей, cookies, API-ключей и содержимого заявлений.

## 11. Визуальная система, UX и доступность

**До кодирования экранов:** Claude представляет три различающиеся **авторские** premium-идеи (токены цветов и типографики, светлая/тёмная стратегия, плотность карточек, иерархия «Сегодня», микровзаимодействия, безопасная палитра контрастности, примеры mobile + desktop). Дима утверждает одно направление или комбинирует. Не копировать конкретные существующие приложения, нельзя использовать официальный логотип.

- Mobile-first от 360 px; нижняя навигация для студента, доступная иерархия у сотрудника; кликабельная область >=44 CSS px там, где возможно; клавиатурный доступ и фокус.
- Семантические подписи полей, понятные ошибки, loading/empty/success/offline, цвет никогда не единственный носитель смысла, учёт `prefers-reduced-motion`.
- Анимации должны объяснять состояние и не создавать задержек. Без тяжёлых background-видео или сложного 3D.
- Упорядоченность «Сегодня»: 1) следующая пара, 2) перенос, 3) ближайший дедлайн, 4) активная заявка, 5) совет планировщика.
- Использовать только материалы с разрешающими лицензиями; зафиксировать в `THIRD_PARTY_LICENSES.md`.

## 12. Тесты и признаки готовности

**Проверки обязательного ядра (P0):**
- login/logout, недоступность закрытых страниц после logout;
- профиль двух пользователей отличается;
- сегодня/неделя, teacher/room, перенос виден одинаково в уведомлении и расписании;
- разные оценки/зачёты и состояние сессии;
- студент создаёт заявку, видит сохранённый статус после refresh и нового входа;
- другой студент не может получить эту заявку/вложение через прямой API/URL (проверять 403/404);
- клиент 360 px, 390 px, desktop: нет непреднамеренного горизонтального скролла, кнопки доступны;
- все данные фиктивные, нет официального лого, заметный дисклеймер;
- production HTTPS, сайт доступен без VPN из России (проверяется человеком в российской сети);
- рабочие demo credentials подготовлены отдельно; аудит зависимостей и секретов.

**Проверки P1/P2:**
- деканат: заявка → проверка → ответ/смена статуса → запись в истории и уведомление студенту;
- преподаватель может менять оценки только по закреплённым курсам (403 на посторонний курс), событие аудируется;
- регистрация создаёт совершенно вымышленный профиль; демо-студент не может стать сотрудником;
- загрузка файла и скачивание только авторизованным участником обработки, отклонение запрещённых форматов и превышения лимита;
- создание и перенос личной задачи, отмечание выполнения; предложение AI Planner нельзя применить без нажатия «Применить»;
- AI API недоступен/бюджет исчерпан: алгоритм продолжает давать план;
- in-app notifications работают независимо от Web Push; поддерживаемые браузеры могут подписаться и отписаться.

Использовать **pytest** для сервера и **Playwright** для сквозных сценариев, отдельно проверять реальную базу на размещённом окружении; нельзя говорить «проверено», если проверка не запускалась.
